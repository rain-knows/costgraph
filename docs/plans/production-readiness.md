# CostGraph 生产准备与长期演进计划

> 状态：计划，未完成。本文记录下一阶段和长期工作的目标，不证明对应能力已经部署或验收。
> 当前能力以代码、迁移、测试和运行手册为准；本文只在这些事实基础上安排后续工作。
> 更新时间：2026-10-21

## 1. 当前判断

CostGraph 已经完成可运行的最小业务闭环：成本事实导入、校验、审批、不可变快照发布、
PostgreSQL 隔离、独立 Worker、Agent Runtime、成本查询、追溯、报表和前端治理工作区均有
代码与自动化验证。

当前最关键的缺口是生产接入和运营保障，而不是继续增加 Agent 数量或堆叠报表。真实外部
OIDC IdP 对接仍未执行；本地 demo 认证、本地 RSA/JWKS 测试和真实 IdP 不等价。导入载荷
当前使用本地内容寻址对象存储，正式多实例部署前必须确定共享且持久化的存储方案。

## 2. 已有验证基线

  不作为本轮审阅修正的验证结果。

- 真实 DeepSeek provider 入口已验证，但这不替代 OIDC、staging 部署或真实业务数据验收。
- `scripts/check_docs_sync.ps1` 与 `git diff --check` 是交付前强制检查。

## 3. P0：完成 staging 生产接入闭环

P0 的完成标准是：一个真实测试租户可以通过真实企业 IdP 登录，并使用接近 ERP/MES 的数据
完成“提交、校验、审批、发布、查询、追溯、报表”全链路；失败发布时旧 published snapshot
仍然可查询；所有证据都来自 staging 运行结果，不使用 local demo auth 代替。

### P0-1 真实 OIDC 验收

使用一个可控的测试 IdP 和一个前端 client，验证以下项目：

- Authorization Code + PKCE、回调、退出和重新登录。
- `issuer`、`audience`、JWKS 签名、`exp`、`iat`、`sub` 和租户/角色 claim。
- `sub` 到 `principal_id` 的映射，以及 OIDC 角色与本地成员关系的交集规则。
- 新主体未建立本地成员关系时返回 403；角色、数据范围和租户越权均被拦截。
- 访问令牌只存在内存中，刷新页面和退出后的行为符合预期。

验收产物：脱敏后的 IdP 配置摘要、登录/退出截图或录屏、401/403 验收结果、staging 日志
和一条可复现命令。不得保存令牌、私钥或 client secret。

### P0-2 明确 staging 拓扑和数据库角色

先固定一套最小部署拓扑：

```text
Browser -> API -> PostgreSQL
                 ^
                 |
              Worker
Browser -> shared import object storage <- API/Worker
```

部署前必须确认：

- API 使用受限的 `costgraph_app` 登录角色，使 RLS 真正生效。
- Worker 使用专用受控角色，负责跨租户领取调度任务，并在领取后按任务租户注入上下文。
- Alembic 迁移只由受控迁移身份执行，API 启动不自动建表。
- API 与 Worker 访问同一个持久化对象存储；多实例不能各自使用本地临时目录。
- `APP_ENV=staging` 时不设置任何本地主体变量，也不启用 `LOCAL_DEMO_AUTH_ENABLED`。
- 健康检查同时区分数据库、迁移 head 和 Worker 心跳；readiness 失败时不接收业务流量。

验收产物：部署配置清单、启动顺序、角色授权 SQL 或基础设施变更记录、健康检查结果和
一份不含密钥的环境变量清单。

### P0-3 真实业务数据全链路

准备一份脱敏的 ERP/MES 导出，至少覆盖多投入、部分领用、批次分流、零/非零不良品、制造
后费用和跨期间查询。按以下顺序验收：

1. API 提交导入任务并验证幂等键、载荷摘要和权限。
2. Worker 执行格式、快照、DAG、业务规则和投影校验。
3. 管理员审批或拒绝；拒绝任务不能进入发布。
4. 发布不可变快照，查询总览、批次详情、来源追溯和两类报表。
5. 注入一次发布失败，确认旧 published snapshot 仍可读，失败批次不可查询。
6. 用第二个主体验证租户、角色和数据范围隔离。

验收产物：任务 ID、快照 ID、发布前后查询结果、失败发布结果、隔离验证结果和脱敏数据
摘要。金额、数量、舍入和快照 ID 以服务端结果为准。

## 4. P1：建立可运营的生产保障

P1 应在业务扩展前完成。系统需要能回答“现在是否可用、哪里变慢、哪批数据失败、能否恢复”。

### P1-1 结构化日志、指标和告警

补齐统一的结构化日志字段：`service`、`environment`、`request_id`、`tenant_id`、
`principal_id`、`job_id`、`run_id`、`snapshot_id`、`status`、`duration_ms` 和错误码；
敏感 token、密码、原始导入载荷和模型密钥不得进入日志。

至少采集并设置告警阈值：

- API 请求错误率、延迟、401/403 比例和 readiness 状态。
- Worker 心跳、领取延迟、租约接管、重试次数、失败任务和并发利用率。
- 导入任务各状态数量与耗时，校验失败率、审批等待时间和发布失败率。
- 成本投影 P50/P95、SQL 数量、结果行数、载荷大小和数据库连接池耗尽。
- 对象存储读写失败、摘要校验失败和备份任务失败。

现有 `backend/scripts/runtime_report.py` 可以作为运行指标的初始数据源；生产环境仍需决定
指标后端、日志保留周期、告警接收人和静默规则，并用 staging 故障注入验证告警确实触发。

### P1-2 备份、恢复和数据保留

为 PostgreSQL、导入对象和审计数据分别定义保留策略。第一版可采用以下待业务确认的目标：

- RPO 不超过 24 小时。
- RTO 不超过 4 小时。
- 至少保留一个可回放的 staging 恢复副本和一份异地或独立存储副本。
- 审计事件保持追加语义，恢复后不能通过应用接口修改或删除。

必须完成一次恢复演练：从备份恢复数据库和对象存储，执行迁移/健康检查，读取旧 published
snapshot，重新验证一条成本追溯链，并记录实际恢复时间、缺失数据和修正措施。没有恢复演练
证据时，不把“已配置备份”写成“可恢复”。

### P1-3 部署、密钥和发布门禁

- 明确 API、Worker、PostgreSQL、对象存储和 IdP 的网络边界。
- 使用环境密钥管理服务保存数据库凭据、OIDC client secret 和 DeepSeek key；日志与构建产物
  不携带密钥。
- staging 发布前自动执行迁移检查、后端全量测试、前端构建/bundle 门禁、文档同步和
  `git diff --check`。
- staging 通过真实 OIDC 和全链路验收后，才允许推广到 production。
- 为 Worker 停止、数据库不可用、对象存储不可用和模型 provider 超时分别记录操作步骤；
  不能把 fixture provider 当作生产故障回退。

## 5. P2：按真实业务需求扩展成本模型

这些项目暂不预建抽象。每个项目开始前，先冻结事实模型、快照边界、权限、计算规则、审计
动作和验收数据，再实现 API、Worker、查询和 UI。

推荐顺序如下：

1. **库存结存和批次余额**：定义期初、入库、领用、结存和跨期间规则，明确它与当前实际
   领用成本图的关系。
2. **返工分支**：定义返工事件、原批次与返工批次关系、成本归集和重复领用防护。
3. **副产品与联产品**：定义产出分摊、可变现价值或其他成本分配规则，并绑定规则版本。
4. **异常工单和质量损失**：把不良、报废、返工和责任归因作为可审计业务事实，而不是模型
   推断结果。
5. **导出与分享**：增加权限受控的 Excel/PDF/CSV 导出，明确快照、筛选条件和生成时间，
   并限制大结果集和敏感数据外发。
6. **预算、标准成本与实际对比**：建立版本化标准成本和期间口径，避免覆盖当前实际成本事实。
7. **ERP/MES/WMS 连接器**：先做一个真实系统的只读同步和失败重试，再扩展更多系统；连接器
   输出必须进入现有导入任务和发布流程，不能旁路写成本事实表。

## 6. 不作为近期重点的工作

- 不增加第二套 Agent 外循环；正式运行面继续保持 PostgreSQL、独立 Worker 和单一 LangGraph
  外循环。
- 不把模型输出当作金额、数量、权限、数据范围、状态或报表事实。
- 不先做多 Agent、复杂插件市场或大规模报表主题扩展。
- 不为已废弃路径增加兼容层、回退机制或迁移方案。

## 7. 建议执行顺序与交付门槛

按最小可运营闭环推进：

| 阶段 | 主要工作 | 结束条件 |
| --- | --- | --- |
| 第 1 阶段 | 真实 OIDC、staging 配置、API/Worker/迁移角色核对 | 真实用户登录，RLS 和角色隔离有证据 |
| 第 2 阶段 | ERP/MES 脱敏数据导入、审批、发布、查询和失败演练 | 全链路通过，旧 published snapshot 可恢复查询 |
| 第 3 阶段 | 结构化日志、指标、告警、备份和恢复演练 | 故障可发现、数据可恢复、RPO/RTO 有实际记录 |
| 第 4 阶段 | 一个真实业务扩展，例如库存结存 | 事实模型、规则版本、权限、测试和 UI 验收齐全 |

每阶段交付前执行：

```powershell
.\scripts\check_docs_sync.ps1
git diff --check
```

涉及数据库、权限、Worker、SSE 或 API 的实现变更，还必须同步对应原子文档和自动化测试；
真实 IdP、真实业务数据、PostgreSQL 集成、离线 Eval 和 fixture 验证分别记录，不能互相替代。
